# pqsession 中继 v2：安全加固版部署说明

本包由四部分组成：

| 文件 | 作用 |
| --- | --- |
| `server.js` | 中继服务器 v2（哑管道；崩溃修复、背压、字节整形、安全默认值、动态 CSP 哈希、本地算法库、可选原生 TLS） |
| `pqsession-net.html` | 前端 v2.1（256 位指纹、房间口令信封、棘轮"先验证后提交"、已核对联系人信任存储、本地算法库优先、去第三方字体） |
| `vendor.mjs` | 把 ML-KEM / hash-wasm 固定到 `./vendor`，打印 SHA-256 |
| `test-relay.mjs`、`test-frontend.mjs`、`test-e2e.mjs` | 不需要安装 ws、不需要联网即可运行的测试（`npm test`）；e2e 用假浏览器把两端跑通全流程含语音 |
| `cert.mjs` | 生成自签名 TLS 证书（`npm run cert`），让局域网部署也能用 https:// |

## 一、最小部署步骤

```bash
npm install                 # 只有 ws 一个依赖
npm run vendor              # 联网一次，把两个算法库固定到 ./vendor（建议换一台机器再跑一次比对哈希）
npm run check               # 自检：CSP 哈希与页内 <meta> 是否一致、vendor 是否齐全、配置是否安全
npm test                    # 30 项测试
TLS_CERT=fullchain.pem TLS_KEY=privkey.pem npm start     # 原生 TLS；或放在反向代理后：TRUST_PROXY=1 npm start
```

浏览器只在安全上下文（https:// 或 localhost）里提供 Web Crypto 与麦克风，纯 http 暴露到公网时页面根本无法工作，`--check` 与启动日志都会警告。

## 二、环境变量（全部可选）

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `PORT` / `HOST` | 8080 / 0.0.0.0 | 监听地址 |
| `TLS_CERT` / `TLS_KEY` | 空 | 同时给出即启用原生 TLS（TLS 1.2+），并自动加 HSTS |
| `TRUST_PROXY` | 关 | 置于反向代理之后才打开：信任 `X-Forwarded-For / -Proto / -Host` |
| `ALLOWED_ORIGINS` | 空（仅同源） | 逗号分隔的 origin 列表；`*` 表示任意（旧版默认行为） |
| `MAX_CONN_PER_IP` | 64 | 每 IP 并发连接上限；0 关闭。反向代理后必须配合 `TRUST_PROXY=1`，否则所有人共享代理 IP |
| `MAX_CONN` | 4096 | 全局并发连接上限；0 关闭 |
| `JOIN_TIMEOUT_MS` | 30000 | 连接后迟迟不 join 的连接被关闭；0 关闭 |
| `MAX_PAYLOAD` | 4 MiB | 单帧上限 |
| `MSG_RATE` / `MSG_BURST` | 2000 / 4000 | 每连接消息条数限流（超额丢弃） |
| `BYTES_RATE` / `BYTES_BURST` | 32 MiB/s / 96 MiB | 每连接字节整形（超额暂停读取，不丢帧）；`BYTES_RATE=0` 关闭 |
| `BP_HIGH` / `BP_LOW` | 8 MiB / 1 MiB | 背压高低水位 |
| `BP_STALL_MS` | 60000 | 对端持续不读超过此时长即判僵死踢出 |
| `HEARTBEAT_MS` | 30000 | 心跳间隔；0 关闭 |
| `VENDOR_DIR` | `./vendor` | 本地算法库目录 |

## 三、已核对联系人（信任存储，v2.1）

- 在「② 连接」面板底部的"已核对的联系人"里管理；只保存指纹、你起的名字和「房间口令哈希 → 上次对方指纹」，不含任何密钥。
- 加密存储：数据用你的身份私钥经 HKDF-SHA-256 派生的 AES-256-GCM 密钥加密后，随本站域名存放在浏览器 localStorage，键名按身份公钥哈希分命名空间。没有载入同一份身份文件就解不开，每个身份各有一份列表；浏览器配置被拷走只拿到密文。无法持久化的环境（隐私模式、预览沙箱）自动退回内存模式并在界面上标明。
- 同一指纹再次出现：自动通过核对并直接握手（相当于 Signal 里"已验证的联系人直接可用"），界面显示"与已核对过的联系人『X』一致"。
- 新指纹出现：若你已核对过别人，界面用警告色列出这些名字，提示"若你在等的正是其中之一，这个新指纹就很可疑"。
- 同一房间口令下对方指纹与上次不同：红色告警，不依赖你有没有起名字。
- 给新指纹起的名字与已有联系人重名：视为"密钥变更"，要求再次点击确认，旧指纹记入该联系人的历史（列表里显示"曾更换密钥 N 次"）。
- 连接中途被替换出现的指纹：即使在列表里也不自动通过，要求重新核对后手动确认。
- 可导出 / 导入 JSON（换浏览器、换域名或换身份时使用；导出为明文需确认，导入等于信任其中的指纹也需确认），可逐条删除或清空。
- 不想留痕就在核对时取消勾选"记住这个指纹"，或事后删除 / 清空。

## 四、语音通话排错

语音走的是同一条端到端棘轮信道，中继看不到内容。它对浏览器环境有三个硬性要求，绝大多数"语音出错"都落在这里：

1. 必须是安全上下文：`https://` 或 `localhost`。用 `http://192.168.x.x:8080` 打开时，浏览器根本不提供 `getUserMedia` 与 `crypto.subtle`，页面顶部会显示红色横幅，日志会写"此环境无法使用麦克风：语音通话需要 HTTPS（或 localhost）"。解决：`npm run cert` 生成自签名证书，然后 `TLS_CERT=cert.pem TLS_KEY=key.pem npm start`，用 `https://<本机IP>:8080` 访问并在证书警告页选择"继续"；或放到带证书的反向代理后并设 `TRUST_PROXY=1`。
2. 麦克风权限：浏览器会记住"拒绝"。日志出现"麦克风权限被拒绝"时，点地址栏左侧的锁形图标把麦克风改回"允许"，再重新发起或接听。
3. 浏览器支持 AudioWorklet：Chrome 66+ / Edge 79+ / Firefox 76+ / Safari 14.1+。若日志显示"语音处理模块（AudioWorklet）装载失败"并提到 CSP，说明前面的反向代理或 CDN 覆盖了本站的 `Content-Security-Policy` 响应头，请保留 `script-src` 里的 `blob:`（中继自带的响应头已经包含）。

定位办法：通话状态栏实时显示"已发 N 包 · 已收 M 包"；挂断时日志会写一行"通话统计"。发包为 0 是采集侧（麦克风 / AudioWorklet）问题，收包为 0 而对方发包正常是链路问题（看中继日志与 `--check`），两者都正常但无声是播放侧（系统输出设备 / 浏览器静音）问题。把日志面板里的红色行原样发给维护者即可。

v2.1.1 起，所有信令发送在一条链上串行、接收端改用 64 位滑动窗口抗重放，消除了并发加密导致帧被误判为重放的可能。

## 五、必须知道的行为变化

1. 前端 v2 与旧版前端不能互通（信令改为口令加密信封）。两端都要用同一版本的页面。
2. 指纹改为 256 位、16 组显示。旧版 8 字节指纹作废，双方需要重新带外核对。
3. 房间号变成"房间口令"：中继只收到它的哈希。口令不区分大小写，忽略空格与连字符。用「随机生成」得到 10 位约 49.5 bit 的口令。
4. Origin 默认仅同源。若页面托管在 A 站、中继在 B 站，B 站需设置 `ALLOWED_ORIGINS=https://A站`。
5. 页面不再向 Google Fonts 发请求。
6. `npm run vendor` 之后，服务器启动时会自动把 `https://esm.sh` 从 CSP 移除；此后页面运行时不再加载任何第三方代码。

## 六、仍然存在的局限（诚实告知）

- 协议与实现均未经独立审计；`@noble/post-quantum` 官方声明未经审计且不防侧信道。
- JS 无法保证擦除内存：本版对临时密钥、链密钥、消息密钥做了尽力而为的清零，但身份私钥在内存中仍是字符串。
- 中继仍看得到 IP、时间、房间口令的哈希、消息大小与节奏（语音通话恒定码率缓解了节奏泄露）。
- 没有事后泄露自愈（post-compromise security）：建议定期结束并重新握手。
- 房间口令信封的强度取决于口令强度；口令被猜中最多暴露身份公钥，聊天内容不受影响。
- 信任存储遵循 TOFU：它记住的是"你自己第一次确认过"的指纹。第一次若没有认真带外核对，之后的"已知联系人"提示也就没有意义。
